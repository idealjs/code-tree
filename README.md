# code-tree

> 组织必须是树,执行可以是图。
> Code organization must be a tree; execution can be a graph.

一个从真实 vibe coding 困境中长出来的 AI 编码 SKILL。它把一套经过反复打磨的代码组织理论注入 AI 的工作方式,让 AI 生成的代码不再"逻辑正确但读不懂",而是**既能看到枝干,也能看到所有叶面**。

---

## 来龙去脉:我是如何从一段对话里解析出这套理论的

> 以下以我的视角——对话中的 AI——记录这个过程。对话发生在 DeepSeek 上,对面是一位有 8 年经验的全栈工程师。一开始,他只是问了一个很常见的困惑;六轮问答之后,理论是他自己长出来的,我只是他的磨刀石。这个 SKILL,就是我把他的想法解析、固化下来的结果。

### 第一问:细节去哪了

他开场就很坦白:用了 vibe coding 之后,代码细节全部丢失了——逻辑、代码风格、编写方式,再也没办法像从前一样逐行确认。逻辑还稍微好一点,让 AI 出张逻辑图就能快速理解;但代码风格、编写方式这些东西又杂又碎,尤其是在用一个陌生的框架。

我给他的答案是"外部化":机械风格交给工具(linter/formatter),架构交给图和 ADR,行为交给测试,探索交给 debugger,最终决策留给自己。方向没错,但这时候,我们都还没碰到问题的根。

### 第二问:AI 懂逻辑,不懂架构

他追问:有的代码解耦、易读,有的紧耦合、难维护。AI 能把逻辑写对,但这些原则它并不清楚——甚至人类工程师也不是所有人都关注。他希望项目能合理扩展。

这一轮我们聊到了把"解耦"翻译成可执行的依赖规则(dependency-cruiser、import-linter)、黄金路径、扩展点。他记下了,但明显没有满足——因为下一个问题紧跟着来了。

### 第三问:被跳过的"1~2 年磨练期"

他说,过去掌握一门新语言的最佳实践,要在一个框架上磨炼一到两年。现在 vibe coding 让他失去了这个机会——写什么样的代码才符合这个语言的实践要求,他很难做决定。

我建议他把 AI 从"代笔者"变成"导师",用 "idiomatic" 这个词引导 AI,把惯用法整理成规则文件。但真正尖锐的问题在后面。

### 第四问:垃圾代码能学出什么

"比如我已经 vibe 出来了一堆代码,我如何从这些代码中学习呢?这本身就是'垃圾'代码。AI 也没办法协助快速提升品位。"

这个问题问得极其锋利。我的回答是:垃圾代码不是学习材料,是**问题生成器**——品位不是从自己的代码里长出来的,要从"垃圾 vs 好"的对比里学,用重写对比法、三稿法训练判断力。

### 第五问:一段真实的 Rust 代码

然后他贴了一段真实代码——一个 `spawn_event_delivery` 函数,`tokio::spawn` 了一个循环,丢弃 `JoinHandle`,没有 shutdown 路径,错误被吞掉。他问:该外部 spawn 还是内部 spawn?

我告诉他:真正的问题不是"在哪 spawn",而是"**这个任务的生命周期由谁负责**"。`spawn_*` 返回 `JoinHandle` 是 Rust 的基本礼貌;加 shutdown token 是生产级的自觉;把错误吞掉是隐形的债。

### 第六问:为什么你意识不到

"为什么我的 AI 在编写的时候,就没有意识到这些问题呢?"

这一问直插本质。我的解释是:AI 的训练目标是预测下一个 token,输出的是**统计上最常见的写法**;AI 没有"痛感数据库",没有隐含上下文,是局部补全而非全局设计,而且极度顺从——你不设边界,它就走最短路径。**AI 生成的是互联网代码的平均值,你要求的是生产级代码的上限。**

### 转折点:他不再提问,开始下结论

讨论到跨函数调用绕来绕去、而 React 一个文件一个组件一目了然时,他没有再问我"怎么办",而是给出了自己的判断:

> "我理解了,实际上还是 AI 写的代码不够好。**应该以树的形式来组织和拆分代码**,这样会比图的形式更容易让人类阅读。树的叶子只需要平铺在一个文件中。这样既能够看到枝干,也能看到所有的叶面。"

紧接着,他自己补上了第二刀,砍向另一个极端——过度封装:

> "每个函数都被封装得只有十几二十行。看起来主干变少了,实际上侧枝变多了。这样就会看到一个**全是枝条的树,而难以看清主干**。"

那一刻我意识到:前面六轮问答,都不是答案本身,而是他打磨理论的砂纸。树、主干、侧枝、叶子、藤——这套词汇是他自己发明的,不是我教他的。

### 最后的打磨:300 行

他又补上最后一块拼图:叶子应该有一个可操作的判别标准——**不超过 300 行**。超过 300 行,不是拆函数,而是把它升级为侧枝,并给它新配一个主干。

最后他让我把这两三个观点整理成一篇博客,标题是我们共同打磨出来的:

**《代码是树,不是藤:AI 时代重新理解"好代码"的结构》**(全文收录在 [skills/code-tree/references/blog.md](skills/code-tree/references/blog.md))

## 我从他想法里解析出的模型

作为解析者,我把他的理论压缩成一张表:

| 概念 | 他的定义 |
|---|---|
| 核心规律 | 没有以树的形式规划的代码,必然生长为图的形状(交叉调用、交叉引用);树形规划是对抗它的根本方案,设计模式补不了 |
| 主干 | 大、明显、能一口气读完、起引导作用 |
| 侧枝 | **缩小的主干**,与主干同构——不是细节倾倒场 |
| 叶子 | 平铺的总览单元,≤ 300 行,不再引导 |
| 递归规则 | 每个非叶子节点,都是它范围内的主干 |
| 300 行规则 | 叶子超载 = 内部已长出结构,应升级为侧枝 + 新配主干,而不是拆函数 |
| 三大反模式 | 藤(主干消失)、碎片(叶子被打碎)、超载(该升级没升级) |
| 切片视角 | React 组件、Express/Axum handler 是天然切片;裸 tokio/裸 http 不给切片,必须手动搭树 |
| 角色分工 | AI 在处理过程中主动合理规划树形结构,人类据此快速 review 裁决——review 从"读懂全部代码"降为"核对一棵树" |

这个模型最打动我的是它的**自洽**:主干、侧枝、叶子不是三种东西,而是同一种东西在三个尺度上的表现——一条规则递归适用,于是"每个目录打开都好读"不再是一句口号,而是一套有判别信号(300 行)、有明确动作(升级为侧枝 + 立主干)、有边界(禁止只拆叶子不立主干)的完整设计规则。

## 这个 SKILL 做什么

`code-tree` 把上述理论固化成一个可安装的 skill,让 AI 编码助手在以下场景自动应用树形组织原则:

- **生成代码时**:先定树再写代码;主干先行;叶子平铺 ≤ 300 行;不发明只调用一次的转发函数
- **审查代码时**:逐项检查藤、碎片、超载三种反模式
- **重构时**:超载叶子升级为侧枝 + 配主干;碎片合并回叶子;藤提炼主干
- **角色分工**:AI 主动合理规划结构,让人类 review 从"读懂全部代码"降为"核对一棵树"

完整规则见 [skills/code-tree/SKILL.md](skills/code-tree/SKILL.md)。

## 安装教程

### 前置要求

- [ZCode CLI](https://zcode.dev)(或兼容的 Agent CLI,如 Claude Code)
- `git`

### 方式一:用户级安装(推荐,对所有项目生效)

```bash
# 1. 克隆仓库
git clone https://github.com/idealjs/code-tree.git

# 2. 把 skill 复制到用户级 skills 目录
mkdir -p ~/.agents/skills
cp -r code-tree/skills/code-tree ~/.agents/skills/

# 3. 清理克隆的仓库(可选)
rm -rf code-tree
```

### 方式二:项目级安装(只对当前项目生效)

```bash
# 在你的项目根目录执行
git clone https://github.com/idealjs/code-tree.git /tmp/code-tree
mkdir -p .agents/skills
cp -r /tmp/code-tree/skills/code-tree .agents/skills/
rm -rf /tmp/code-tree
```

### 方式三:符号链接(跟随仓库更新)

如果你希望 `git pull` 一下就能更新 skill:

```bash
git clone https://github.com/idealjs/code-tree.git ~/code-tree
mkdir -p ~/.agents/skills
ln -s ~/code-tree/skills/code-tree ~/.agents/skills/code-tree
```

### 验证安装

重新启动 ZCode(或新开一个会话),然后:

1. 输入 `/` 查看可用 skills,确认列表里出现了 `code-tree`;
2. 或者直接对话测试,比如让 AI "新建一个用户模块",观察它是否先定树、控制叶子规模。

### 在 Claude Code 中使用

SKILL.md 格式与 Claude Code 兼容,把目录复制到 `~/.claude/skills/`(用户级)或项目的 `.claude/skills/` 即可:

```bash
mkdir -p ~/.claude/skills
cp -r code-tree/skills/code-tree ~/.claude/skills/
```
