# 代码是树，不是藤：AI 时代重新理解"好代码"的结构

> 本文整理自一段真实的人机对话：一位 8 年经验的全栈工程师在与 AI 反复讨论 vibe coding 的困境后，最终自己推导出的一套代码组织理论。它是 [code-tree](../../README.md) 这个 SKILL 的理论源头。

用 AI 写了几个月代码之后，我陷入一种奇怪的状态：功能能跑，逻辑正确，测试也过，但我读不懂自己的项目了。

不是读不懂某一行，而是读不懂结构。函数绕来绕去，主体找不到，主干看不见。我一度以为是自己老了，或者是 Rust 太陌生。后来发现，问题不在我，也不在语言，而在于 AI 默认生成的代码，从结构上就是错的。

这篇文章讲一个我反复打磨后定下来的模型：**代码组织必须是树，执行可以是图；树是递归的，主干、侧枝、叶子是同一件事在不同尺度上的表现。**

## 一、树是组织，图是执行

写 React 时，代码结构很清晰：一个文件一个组件，组件就是主体，props 向下、事件向上。打开一个文件，你就看到一个完整的东西。

写 Express、Koa、Fastify 时也一样：一个 route handler 就是一个切片，主体清晰，主干平铺。打开一个文件，你就看到一条完整的处理链。

转到 Rust + tokio 后，这种直觉失效了。函数绕来绕去，跨文件调用，主体找不到。

我一度以为这是"前端 vs 后端"的差异。后来发现不对。真正的分界线是：**框架给不给你"切片"作为主体。**

| 场景 | 有切片供给 | 默认形态 |
|---|---|---|
| React 组件 | ✅ | 树 |
| Express/Koa/Fastify handler | ✅ | 树 |
| Axum/Actix handler | ✅ | 树 |
| 裸 tokio / 后台任务 | ❌ | 图 |
| 裸 http / 裸 goroutine | ❌ | 图 |

面向切片的框架（React、Express、Koa、Fastify、Axum、Gin）默认给你树——因为它们提供了 handler、ctx、next、props 这些天然的主体单位。操作原语的代码（裸 tokio、裸 http、裸 goroutine）默认给你图——因为没有主体可依附，执行图全部暴露在你面前。

关键区分：

| | 树（组织） | 图（执行） |
|---|---|---|
| 作用 | 让人能找到代码 | 让程序能跑 |
| 可见性 | 目录结构、模块边界 | 调用链、事件流 |
| 好代码 | 树清晰，边界明确 | 图被限制在树内 |
| 坏代码 | 树混乱或没有树 | 图跨越所有枝干 |

**好代码 = 清晰的树 + 被约束在树内的图。** 所谓"解耦"，本质就是把图约束在树内。

## 二、树是递归的：主干、侧枝、叶子是同一件事

这是我这套模型里最关键的一点，也是我花了很久才想清楚的：

**主干、侧枝、叶子不是三种不同的东西，是同一种东西在三个尺度上的表现。**

- **主干**：大、明显、能一口气读完、起引导作用。
- **侧枝**：不是"细节的收纳处"，而是缩小的主干。脱离主干视角后，侧枝本身仍然要大、明显、起引导作用。它和主干同构，只是尺度不同。
- **叶子**：平铺，提供总览，不再引导。

换句话说：**每个非叶子节点，都是它范围里的主干。**

一条规则，递归适用：

> 每个非叶子节点，都应该像主干一样大、明显、起引导作用。

这比"主干一口气读完、侧枝可以深"精确得多。后者暗示侧枝是细节垃圾桶，是错的。**侧枝是迷你主干，它本身也要清晰。**

## 三、叶子的判别规则：300 行

叶子是平铺的总览单元。它有一个可操作的判别标准：

> 一片叶子不应超过 300 行。超过 300 行，它就不再是叶子。

300 行不是精确科学，但它对应一个真实认知边界：一屏约 50~80 行，300 行约 4~6 屏，大致是一个能"一眼总览"的量级。

超过 300 行意味着什么？

**它意味着这片"叶子"内部其实已经长出了结构，只是被压平了。** 内部有多个主体、多个职责、多个可引导的段落，但因为没有枝干，全挤在一起。

正确的动作不是"继续往里塞"，也不是"随便拆几个函数"，而是：

> 把它提升为侧枝，并给它配一个主干来组合。

```text
之前：
    parent/
    └── big_leaf.rs        ← 800 行，什么都往里塞

之后：
    parent/
    └── big_leaf/          ← 升级为侧枝
        ├── mod.rs         ← 主干：引导 + 组合
        ├── part_a.rs      ← 叶子
        ├── part_b.rs      ← 叶子
        └── part_c.rs      ← 叶子
```

mod.rs 是新长出来的主干。它不大，但清晰、起引导作用。三片新叶子各自平铺，各自在 300 行内。结构从"一片超载的叶子"变成"一个侧枝 + 三片叶子"。

**关键：提升为侧枝时，必须同时长出一个主干。** 只拆叶子、不立主干，就是把树拆成了藤。这是 AI 最常犯的错。

## 四、三个反模式：藤、碎片、超载

按这个模型，坏代码只有三种形态：

**1. 藤（主干消失）**
每个函数 10~20 行，每个只被调用一次，函数名比函数体还长。读代码像走迷宫，进去、跳转、返回、再跳转，看完一圈还是不知道主流程是什么。主干被侧枝淹没。

**2. 碎片（叶子被打碎）**
本该是叶子的东西被拆成转发函数。一个 60 行的编排被切成六个 10 行的 `validate_and_build`、`save_and_publish`，每个都不隐藏复杂度，只是让主干多几次跳转。这不是侧枝，是叶子被伪装成侧枝。

**3. 超载（叶子变侧枝却没升级）**
一个文件 800 行，什么都往里塞。内部已经有结构，但拒绝长出主干。

三个反模式的病根是同一个：**没有在每个尺度上维护"主干要引导、叶子要平铺"这条递归规则。**

## 五、为什么 AI 默认做不到

这不是 AI 的失败，是它的目标函数决定的。

大模型的训练目标是"预测下一个 token"，输出的是统计上最常见的写法，不是最好的写法。而"最常见"意味着：

- 大量教程和 demo 的碎片化写法
- 大量被误读的"小函数"教条
- 大量按功能切碎的"一个东西一个文件"

AI 没有"主干"概念，也没有"树"概念。它在局部判断"这个能拆吗"，不判断"拆了之后整体还读得懂吗"。它没有经历过：

- 半夜被 page 起来排查一个跨五层调用的 bug
- 接手一个打开十个文件才能看懂一个流程的项目
- 因为过度抽象导致简单需求改了三天

**AI 缺的不是知识，是痛感。** 你多年经验里最值钱的，不是记住每个细节，而是"这不对"的直觉——这种直觉来自真实的生产事故和长期的维护痛苦。

## 六、把树形思维写进协作流程

既然 AI 默认做不到，就把它变成约束喂给它。

**提示词模板（生成前）：**

```text
用 <语言> 实现这个用例。

先写主干：大、明显、能一口气读完，只放"下一步去哪"的引导。

侧枝是缩小的主干，和主干同构，脱离主干视角后它自己也要清晰。

叶子平铺，提供总览，目标 ≤ 300 行。

文件超过 300 行时，提升为侧枝，新建 mod.rs 作为主干组合，不要继续往里加函数。

不要把主干切成只调用一次的转发函数。
```

**审查提示词（生成后）：**

```text
检查这次变更：

主干函数是否清晰可见、能一口气读完？

每个非叶子节点是否像主干一样起引导作用？

有没有只调用一次、没有引导作用的转发函数？

有没有文件超过 300 行却未升级为侧枝？

有没有只拆叶子、没立主干的情况？
```

**项目规则（RULES.md）：**

```text
每个非叶子节点，都要像主干一样：大、明显、可一口气读完、起引导作用。

叶子平铺，目标 ≤ 300 行。

超过 300 行：升级为侧枝 + 新增长主干，不要拆函数。

禁止藤、碎片、超载三种形态。

跨模块调用必须走显式接口。
```

## 结语

AI 让写代码变快了，但让读懂代码变难了。这不是因为我们退化了，而是因为 AI 默认生成的是"能跑的代码"，不是"能维护的代码"。

能跑的代码和执行图有关，能维护的代码和组织树有关。AI 擅长生成前者，人类必须负责后者。

组织必须是树：主干引导全局，侧枝是缩小的主干，叶子平铺成总览。每个尺度上都要可读——这才是"既能看到枝干，也能看到所有叶面"。

叶子超过 300 行，不是拆函数，是升级为侧枝，并给它配一个主干。别让 AI 把树写成藤。

**执行可以是图，组织必须是树。** 这大概就是 AI 时代，一个工程师还能守住的最后一点品味。
