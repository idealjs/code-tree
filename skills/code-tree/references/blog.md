# 代码是树，不是藤：AI 时代重新理解"好代码"的结构

> 本文整理自一段真实的人机对话：一位 8 年经验的全栈工程师在与 AI 反复讨论 vibe coding 的困境后，自己推导出的一套代码组织理论，并在随后的工程实践中持续打磨成形。它是 [code-tree](../../README.md) 这个 SKILL 的理论源头。

用 AI 写了几个月代码之后，我陷入一种奇怪的状态：功能能跑，逻辑正确，测试也过，但我读不懂自己的项目了。

不是读不懂某一行，而是读不懂结构。函数绕来绕去，主体找不到，主干看不见。那种感觉甚至有一种回到刚开始入行写代码的时候——像个新人一样，面对代码理不清结构。后来发现，问题不在我，也不在语言，而在于 AI 默认生成的代码，从结构上就是错的。

这篇文章讲一个我反复打磨后定下来的模型：**没有以树的形式规划的代码，必然生长为图的形状；对抗它的方式，是把组织本身规划成树——主干、侧枝、叶子，是同一件事在三个尺度上的表现。**

## 一、不规划，必成图

写 React 时，代码结构很清晰：一个文件一个组件，组件就是主体，props 向下、事件向上。打开一个文件，你就看到一个完整的东西。

写 Express、Koa、Fastify 时也一样：一个 route handler 就是一个切片，主体清晰，主干平铺。打开一个文件，你就看到一条完整的处理链。

转到 Rust + tokio 后，这种直觉失效了。函数绕来绕去，跨文件调用，主体找不到。

我一度怀疑，是不是自己过于依赖过去特定框架的经验，才导致在学习新内容时这么不适应。后来发现，问题也不在这儿。真正的分界线是：**框架给不给你"切片"作为主体。**

| 场景 | 有切片供给 | 默认形态 |
|---|---|---|
| React 组件 | ✅ | 树 |
| Express/Koa/Fastify handler | ✅ | 树 |
| Axum/Actix handler | ✅ | 树 |
| 裸 tokio / 后台任务 | ❌ | 图 |
| 裸 http / 裸 goroutine | ❌ | 图 |

面向切片的框架（React、Express、Koa、Fastify、Axum、Gin）替你做了规划——handler、ctx、next、props 这些天然的主体单位就是现成的骨架，树自然形成。操作原语（裸 tokio、裸 http、裸 goroutine）没人替你规划，代码就按最短路径生长：函数交叉调用，数据交叉引用，默认长成图。

所以我把这个观察推成一般规律：**没有以树的形式规划的代码，必然生长为图的形状。**

- **图**（交叉调用、交叉引用）是代码失去规划后的形状。它能跑，但没人能读懂。
- **树**（目录结构、模块边界）是对生长的主动规划：目录层级和模块边界，就是刻意压住图化生长的骨架。

| | 树（组织） | 图（执行） |
|---|---|---|
| 作用 | 让人能找到代码 | 让程序能跑 |
| 可见性 | 目录结构、模块边界 | 调用链、事件流 |
| 好代码 | 树清晰，边界明确 | 图被限制在树内 |
| 坏代码 | 树混乱或没有树 | 图跨越所有枝干 |

**好代码 = 清晰的树 + 被约束在树内的图。** 所谓"解耦"，本质就是把图约束在树内。

## 二、设计模式救不了它

看清"必成图"这个规律后，我回头看自己学过的那些设计模式，结论让我不舒服：**它们大多是在图状代码上打补丁。**

再加一层抽象，再包一层间接，再引入一个 manager——每一次修补都让跳转更多、包装更厚，读代码的负担更重。设计模式徒增编码困境：它没有指出根本问题——结构从未以树的形式被规划——自然也给不出对应的解决方案。

根本解只有一个：动手之前，先把树规划出来。

## 三、树是递归的：主干、侧枝、叶子是同一件事

这是我这套模型里最关键的一点，也是我花了很久才想清楚的：

**主干、侧枝、叶子不是三种不同的东西，是同一种东西在三个尺度上的表现。**

- **主干**：大、明显、能一口气读完、起引导作用。
- **侧枝**：不是"细节的收纳处"，而是缩小的主干。脱离主干视角后，侧枝本身仍然要大、明显、起引导作用。它和主干同构，只是尺度不同。
- **叶子**：平铺，提供总览，不再引导。

换句话说：**每个非叶子节点，都是它范围里的主干。**

一条规则，递归适用：

> 每个非叶子节点，都应该像主干一样大、明显、起引导作用。

这比"主干一口气读完、侧枝可以深"精确得多。后者暗示侧枝是细节垃圾桶，是错的。**侧枝是迷你主干，它本身也要清晰。**

## 四、叶子的判别规则：300 行

叶子是平铺的总览单元。它有一个可操作的判别标准：

> 一片叶子不应超过 300 行。超过 300 行，它就不再是叶子。

300 行不是精确科学，但它对应一个真实认知边界：一屏约 50~80 行，300 行约 4~6 屏，大致是一个能"一眼总览"的量级。

超过 300 行意味着什么？

**它意味着这片"叶子"内部其实已经长出了结构，只是被压平了。** 内部有多个主体、多个职责、多个可引导的段落，但因为没有枝干，全挤在一起。

正确的动作不是"继续往里塞"，也不是"随便拆几个函数"，而是：

> 把它提升为侧枝，并给它配一个主干来组合。

```text
之前：
    parent/
    └── billing.rs         ← 800 行，发票/支付/退款全塞在一起

之后：
    parent/
    └── billing/           ← 升级为侧枝
        ├── mod.rs         ← 主干：组合 + 引导
        ├── invoice.rs     ← 叶子：发票主体
        ├── payment.rs     ← 叶子：支付主体
        └── refund.rs      ← 叶子：退款主体
```

mod.rs 是新长出来的主干。它不大，但清晰、起引导作用。三片新叶子各自平铺，各自在 300 行内。注意叶子的命名：invoice、payment、refund，每一片都对应文件内部真实长出的一个主体——而不是 part_a、part_b 这样的切割顺序，后者恰恰是要禁止的机械拆分。结构从"一片超载的叶子"变成"一个侧枝 + 三片叶子"。

**关键一：提升为侧枝时，必须同时长出一个主干。** 只拆叶子、不立主干，就是把树拆成了藤。这是 AI 最常犯的错。

**关键二：提升不是机械拆分。** 300 行是触发信号，不是切割指令。切分线必须落在叶子内部已经长出的真实结构上——按主体、职责划分，让每一片新叶子都是一个完整、自洽的主体；不按行数均分，不按函数数量凑，不为了拆而拆。如果找不到自然的切分线，说明结构其实还没长好：先厘清职责，再动手，而不是硬切。机械拆出来的"叶子"互相纠缠、各自残缺，本质仍是碎片。

## 五、三个反模式：藤、碎片、超载

按这个模型，坏代码只有三种形态：

**1. 藤（主干消失）**
每个函数 10~20 行，每个只被调用一次，函数名比函数体还长。读代码像走迷宫，进去、跳转、返回、再跳转，看完一圈还是不知道主流程是什么。主干被侧枝淹没。

**2. 碎片（叶子被打碎）**
本该是叶子的东西被拆成转发函数。一个 60 行的编排被切成六个 10 行的 `validate_and_build`、`save_and_publish`，每个都不隐藏复杂度，只是让主干多几次跳转。这不是侧枝，是叶子被伪装成侧枝。

**3. 超载（叶子变侧枝却没升级）**
一个文件 800 行，什么都往里塞。内部已经有结构，但拒绝长出主干。

三个反模式的病根是同一个：**没有在每个尺度上维护"主干要引导、叶子要平铺"这条递归规则。**

## 六、为什么 AI 默认做不到

这不是 AI 的失败，是它的目标函数决定的。

大模型的训练目标是"预测下一个 token"，输出的是统计上最常见的写法，不是最好的写法。而"最常见"意味着：

- 大量教程和 demo 的碎片化写法
- 大量被误读的"小函数"教条
- 大量按功能切碎的"一个东西一个文件"

AI 没有"主干"概念，也没有"树"概念。它在局部判断"这个能拆吗"，不判断"拆了之后整体还读得懂吗"。它没有经历过：

- 半夜被 page 起来排查一个跨五层调用的 bug
- 接手一个打开十个文件才能看懂一个流程的项目
- 因为过度抽象导致简单需求改了三天

**AI 缺的不是知识，是痛感。** 你多年经验里最值钱的，不是记住每个细节，而是"这不对"的直觉——这种直觉来自真实的生产事故和长期的维护痛苦。

## 七、把树形思维写进协作流程

既然 AI 默认做不到，就把它变成约束喂给它——并且让 AI 主动承担结构规划。

**先规划，后编码（AI 的职责）。** 结构规划是 AI 在处理过程中的职责，不是等人下达的输入。每次动手前，AI 先在回复开头给出简短的结构规划——这个变更落在树的哪里、主干和叶子怎么安排——再写代码。正因为 AI 已经把树搭好，人类的 review 才能从"读懂全部代码"降为"核对一棵树"。

**提示词模板（生成前）：**

```text
用 <语言> 实现这个用例。

先写主干：大、明显、能一口气读完，只放"下一步去哪"的引导。

侧枝是缩小的主干，和主干同构，脱离主干视角后它自己也要清晰。

叶子平铺，提供总览，目标 ≤ 300 行。

文件超过 300 行时，提升为侧枝，新建 mod.rs 作为主干组合，不要继续往里加函数。

提升时沿真实长出的主体边界切分，不要按行数均分、不要为拆而拆。

不要把主干切成只调用一次的转发函数。
```

**审查提示词（生成后）：**

```text
检查这次变更：

主干函数是否清晰可见、能一口气读完？

每个非叶子节点是否像主干一样起引导作用？

有没有只调用一次、没有引导作用的转发函数？

有没有文件超过 300 行却未升级为侧枝？

升级时是否新配了主干、沿真实主体边界切分？

有没有只拆叶子、没立主干的情况？
```

**项目规则（RULES.md）：**

```text
每个非叶子节点，都要像主干一样：大、明显、可一口气读完、起引导作用。

叶子平铺，目标 ≤ 300 行。

超过 300 行：升级为侧枝 + 新增长主干，不要拆函数。

升级时沿真实主体边界切分，禁止机械均分。

禁止藤、碎片、超载三种形态。

跨模块调用必须走显式接口。
```

## 结语

AI 让写代码变快了，但让读懂代码变难了。这不是因为我们退化了，也不是因为语言陌生——而是因为没有被规划成树的代码，必然长成图。

能跑的代码和执行图有关，能维护的代码和组织树有关。AI 擅长生成前者，人类必须负责后者——或者说，人类负责核对 AI 交出的那棵树。

组织必须是树：主干引导全局，侧枝是缩小的主干，叶子平铺成总览。每个尺度上都要可读——这才是"既能看到枝干，也能看到所有叶面"。

叶子超过 300 行，不是拆函数，是升级为侧枝，并给它配一个主干；切分要沿着真实长出的结构，而不是机械地切。别让 AI 把树写成藤。

**执行可以是图，组织必须是树；而树，必须被刻意规划出来。** 这大概就是 AI 时代，一个工程师还能守住的最后一点品味。
