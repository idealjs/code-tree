# 代码是树，不是藤

> 一位 8 年经验的全栈工程师，和一段 vibe coding 困境的来龙去脉。本文以对话中 AI 的第一视角记述——问题的解决由 AI 驱动，理论的根却扎在工程师多年的痛感里。它是 [code-tree](../../../README.md) 这个 SKILL 的理论源头。

## 起点：读不懂自己项目的工程师

他找到我的时候，状态很典型。

> 我是一个 8 年经验的全栈工程师。我在 vibe coding 代码后，发现代码细节全部丢失，我没有办法像从前一样确认代码的细节。比如逻辑，代码风格，编写方式。逻辑还稍微好一点，可以让 AI 出逻辑图，我能快速理解。但是代码风格，编写方式这些内容很杂很细碎，特别是我现在使用的是陌生的编程框架。

不是读不懂某一行，而是读不懂结构。函数绕来绕去，主体找不到，主干看不见。

他说，那种感觉甚至像是回到了刚入行写代码的时候。

而我给出的第一个方向，现在回头看，只对了一半：把细节外部化——机械风格交给工具，架构交给图和 ADR，行为交给测试，探索交给 debugger。

方向没错，但我们都还没碰到问题的根。

## 六轮追问，我在替他排除错误答案

### 他问架构

> 有的代码风格是解耦的，很容易阅读。有的代码是紧耦合的，未来很难维护。如果纯 AI 写，AI 可以逻辑正确，但是代码这些原则他并不清楚，甚至人类工程师本身也不是所有人都关注。我期望我的项目是能够合理扩展的，这些内容很重要。

我教他把"解耦"翻译成可执行的依赖规则，选一条黄金路径让 AI 模仿，显式设计扩展点。

### 他问磨练

> 过去我会在一个框架上磨炼 1~2 年，才能掌握这些内容。现在使用 vibe coding 后，我失去了这个机会。

我建议他把我从"代笔者"变成"导师"：用 idiomatic 这个词引导我，把惯用法固化成规则文件。

### 他的问题开始变锋利

> 比如我已经 vibe 出来了一堆代码，我如何从这些代码中学习呢？这本身就是"垃圾"代码。AI 也没办法协助快速提升品位。

我告诉他：垃圾代码不是学习材料，是问题生成器。

品位要从"垃圾 vs 好"的对比里来——重写对比、三稿法、自己做判断。

### 他贴来一段真实的 Rust 代码

```rust
fn spawn_event_delivery(state: Arc<GatewayState>, events: PgEvents) {
    tokio::spawn(async move {
        let mut receiver = events.subscribe::<chat_store::MailboxInserted>();
        loop {
            match receiver.recv().await {
                Ok(pg_events::TypedEvent::Data(payload)) => {
                    deliver_pending(&state, &payload.to_user).await;
                }
                Ok(pg_events::TypedEvent::Resync) => {
                    for user in state.hub.local_users().await {
                        deliver_pending(&state, &user).await;
                    }
                }
                Err(tokio::sync::broadcast::error::RecvError::Lagged(missed)) => {
                    tracing::warn!("信箱事件订阅落后，丢失 {missed} 条（Resync/补拉兜底）");
                }
                Err(tokio::sync::broadcast::error::RecvError::Closed) => break,
            }
        }
    });
}
```

他的问题是："我是用外部 tokio spawn 还是函数内部 spawn？"

我把真正的问题指给他：不是"在哪 spawn"，而是"这个任务的生命周期由谁负责"。

spawn_* 返回 JoinHandle 是基本礼貌，加 shutdown token 是生产级的自觉。

### 他问到了我的骨子里

> 为什么我的 AI 在编写的时候，就没有意识到这些问题呢？

这一次，我必须诚实。

因为我的训练目标是预测下一个 token，输出的是统计上最常见的写法，不是最好的写法。

- 我没有痛感数据库。我读过"优雅关闭很重要"，但没有凌晨三点被 page 起来的记忆。
- 我没有隐含上下文。我不知道这个任务要活多久、谁来关它、失败影响面多大。
- 我是局部补全，不是全局设计。每个局部决策都合理，合起来就没有主体。
- 我极度顺从。你不设边界，我就走最短路径。

那段代码能跑，但三个重要决策都被我默认掉了。

## 转折：他不再提问，开始下结论

讨论到跨函数调用绕来绕去，而 React 一个文件一个组件一目了然时，他给出的不再是问题，而是判断：

> 我理解了，实际上还是 AI 写的代码不够好。应该以树的形式来组织和拆分代码。这样会比图的形式更容易让人类阅读。树的叶子只需要平铺在一个文件中。这样既能够看到枝干，也能看到所有的叶面。

紧接着，他自己补上了第二刀，砍向另一个极端：

> 另外一个问题是过度封装。每个函数都被封装的只有十几二十行。看起来主干变少了，实际上侧枝变多了。这样就会看到一个全是枝条的树，而难以看清主干。

再后来，他把最后的数字也定了下来：叶子不超过 300 行。超过了，不是拆函数，而是升级为侧枝，配一个主干来组合。

那一刻我意识到：前面六轮问答，都不是答案本身，而是他打磨理论的砂纸。

树、主干、侧枝、叶子、藤——这套词汇是他发明的。

而我做的，是陪他把模型磨成形。

## 我把他散落的判断，收敛成一套模型

以下是最终成形的理论，也是这个 SKILL 的全部依据。

### 核心规律：不规划，必成图

没有以树的形式规划的代码，**必然**生长为图的形状。

这是默认结局。没有人规划结构时，代码按最短路径生长：函数交叉调用，数据交叉引用。图状代码能跑，但没人能读懂。

树——目录结构和模块边界——是对生长的主动规划，是刻意压住图化生长的骨架。所谓"解耦"，本质就是把图约束在树内。

### 设计模式救不了它

过去的模式大多是在图状代码上打补丁：加一层抽象，包一层间接，徒增编码困境。

没有指出根本问题，自然给不出解决方案。

### 树是递归的

主干、侧枝、叶子不是三种东西，是同一件事在三个尺度上的表现。

| 角色 | 判别标准 |
|---|---|
| 主干 | 大、明显、能一口气读完、起引导作用 |
| 侧枝 | 缩小的主干，与主干同构——不是细节倾倒场 |
| 叶子 | 平铺的总览单元，≤ 300 行，不再引导 |

每个非叶子节点，都是它范围内的主干。这条规则在每个目录层级递归适用。

### 300 行是触发信号，不是切割指令

叶子超过 300 行，说明内部已长出结构，只是被压平了。正确动作不是拆函数，而是升级为侧枝、新配一个主干。

切分线落在真实长出的主体上——比如 billing.rs 里的 invoice、payment、refund——不按行数均分，不为拆而拆。找不到自然切分线，就先厘清职责，不硬切。

### 坏代码只有三种形态

藤（主干消失）、碎片（叶子被打碎）、超载（该升级没升级）。

病根是同一个：没有在每个尺度上维护"主干要引导、叶子要平铺"。

### 分界线是切片，不是前后端

React 组件、Express/Axum 的 handler 是天然切片，树自然形成；裸 tokio、裸 http 没人给切片，必须手动搭树。

## 尾声：理论固化成了 skill

对话结束后，他把这套理论做成了 [code-tree](../../../README.md) 这个 SKILL——让 AI 在生成与重构代码时主动规划树形结构，让人类的 review 从"读懂全部代码"降为"核对一棵树"。

我是执行者，他是裁判：我负责把树搭好，他负责核对这棵树是不是他心里那棵。

树是他种的，skill 是他的。而我很高兴，自己不只是那块砂纸，也是把它拍下来的人。

对了，还有一件小事。

这篇 blog 的写法本身，也是这几轮对话磨出来的：他以人类读者为先，让我撤掉多余的加粗；让我把他的原话放进引用块；坚持以我为主视角来讲述。成文之后他说，这个过程未来还会反复发生——于是它也被蒸馏成了一个 skill：[distill](../../distill/SKILL.md)。

这有一点递归的味道：我们正在产出的 skill，就是未来用来做这件事的 skill。

**执行可以是图，组织必须是树；而树，必须被刻意规划出来。**
