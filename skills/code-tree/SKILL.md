# Code Tree:组织必须是树,执行可以是图

一套代码组织理论,来自一位 8 年经验全栈工程师在 vibe coding 实践中的反复打磨。它回答一个问题:**AI 生成的代码逻辑正确,为什么读不懂?** 答案:组织结构错了。本 skill 的职责是让生成的代码在结构上可读——让人类既能看到枝干,也能看到所有叶面。

## 核心模型

**执行可以是图,组织必须是树。**

- **图**(调用链、事件流、数据流)是代码"怎么跑"——它让程序能运行。
- **树**(目录结构、模块边界)是代码"在哪找"——它让人类能读懂。

好代码 = 清晰的树 + 被约束在树内的图。所谓"解耦",本质就是把图约束在树内。图跨越所有枝干,就是坏代码。

## 三个角色:主干、侧枝、叶子

关键认知:**三者不是三种东西,是同一件事在三个尺度上的表现。**

| 角色 | 定义 | 判别标准 |
|---|---|---|
| 主干 | 起引导作用的主体 | 大、明显、能一口气读完 |
| 侧枝 | **缩小的主干**,不是细节倾倒场 | 与主干同构:大、明显、起引导作用 |
| 叶子 | 平铺的总览单元 | ≤ 300 行,不再引导,一眼总览 |

递归规则:**每个非叶子节点,都是它范围内的主干。** 这条规则在每个目录层级适用——目录树的第一层如此,第五层也如此。

特别警惕对侧枝的误解:侧枝不是"可以乱一点的地方"。脱离主干视角后,侧枝自己仍然要大、明显、起引导作用。把细节倾倒进侧枝,长出来的是藤。

## 300 行规则

一片叶子不应超过 300 行(一屏约 50~80 行,300 行约 4~6 屏,是"一眼总览"的认知边界)。

叶子超过 300 行,说明它内部已经长出了结构,只是被压平了。正确的动作:

**不是拆函数,而是升级为侧枝 + 新配一个主干。**

```text
之前(超载的叶子):
    parent/
    └── big_leaf.rs        ← 800 行,什么都往里塞

之后(升级为侧枝):
    parent/
    └── big_leaf/
        ├── mod.rs         ← 新长出来的主干:引导 + 组合
        ├── part_a.rs      ← 叶子
        ├── part_b.rs      ← 叶子
        └── part_c.rs      ← 叶子
```

关键:提升为侧枝时,**必须同时长出一个主干**。只拆叶子、不立主干,就是把树拆成了藤——这是 AI 最常犯的错。

同样重要:**升级不是机械拆分。** 300 行是触发信号,不是切割指令。切分线必须落在叶子内部已经长出的真实结构上——按主体、职责划分,让每一片新叶子都是一个完整、自洽的主体;不按行数均分,不按函数数量凑,不为了拆而拆。找不到自然的切分线,说明结构其实还没长好(或命名没理清):先厘清职责(必要时询问用户),再动手,而不是硬切。机械拆出来的"叶子"互相纠缠、各自残缺,本质仍是碎片。

## 三大反模式

| 反模式 | 形态 | 病根 |
|---|---|---|
| 藤 | 每个函数 10~20 行、只被调用一次,函数名比函数体还长,读代码像走迷宫 | 主干消失 |
| 碎片 | 本该平铺的叶子被切成转发函数,只增加跳转、不隐藏复杂度 | 叶子被打碎 |
| 超载 | 单文件数百行,内部已有结构却拒绝长出主干 | 叶子该升级没升级 |

三者的病根是同一个:**没有在每个尺度上维护"主干要引导、叶子要平铺"这条递归规则。**

## 实操规则

### 生成代码时

1. **先定树,再写代码。** 动手前明确:这个变更落在树的哪个位置?主干是什么?叶子是什么?
2. **主干先行。** 模块入口文件起引导作用,能一口气读完,只放"下一步去哪"的引导,不放实现细节。
3. **叶子平铺。** 一个文件一个主体,目标 ≤ 300 行,提供总览。
4. **文件超过 300 行时**,提升为目录 + 新建主干文件组合,不要继续往里加函数;组合方式按内部真实主体划分,不做机械拆分(见"300 行规则")。
5. **不要发明只调用一次的转发函数**;不为拆而拆。
6. 跨模块调用必须走显式接口,不碰对方内部实现。

### 审查代码时

逐项检查:

- 主干是否清晰可见、能一口气读完?
- 每个非叶子节点是否像主干一样起引导作用?
- 有没有只调用一次、没有引导作用的转发函数?(碎片)
- 有没有文件超过 300 行却未升级为侧枝?(超载)
- 有没有只拆叶子、没立主干的情况?(藤)
- 超载叶子升级为侧枝时,新叶子是否各自为完整主体?有没有按行数均分、硬切出来的残缺碎片?(机械拆分)
- 执行图(调用链)是否被约束在树内?有没有跨越多个枝干的调用?

### 重构时

- 超载叶子 → 升级为侧枝,配新主干;沿真实主体边界切分,不机械均分。
- 碎片 → 合并回叶子,恢复平铺总览。
- 藤 → 提炼主干:把主流程显式地写在一个能一口气读完的地方。

## 框架切片视角

框架提供的"切片"是天然的主干/叶子单位,优先使用它们:

- **有切片供给**(树自然形成):React 组件、Express / Koa / Fastify / Axum / Gin 的 handler。一个文件一个组件、一个 handler 一条完整处理链。
- **无切片供给**(默认长成图):裸 tokio 后台任务、裸 http、裸 goroutine。此时必须手动搭树:显式建模块目录和主干文件,把执行图关进树里。

## 角色分工

**结构规划是 AI 在处理过程中的职责,不是等人下达的输入。** 生成或重构代码时,AI 应主动按本理论合理规划树形结构——先定树、主干先行、叶子平铺——而不是放任结构随意生长,也不是把每个结构决策都推给人类。

**人类负责 review 与裁决。** 正因为 AI 已经把树搭好,review 才会快:扫一眼主干就能确认组织是否合理,而不必在混乱结构里逐文件考古。AI 优化的是"下一个 token 最可能的写法"(统计上最常见),不是"结构上最好",所以人类的 review 不可省略——但有了清晰的树,review 从"读懂全部代码"降为"核对一棵树"。

实操:接到编码指令时,先在回复开头给出简短的结构规划(落在树的哪里、主干/叶子怎么安排),再动手写;涉及业务边界的重大分歧点,向用户确认后再继续。
